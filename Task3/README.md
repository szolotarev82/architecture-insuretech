# Проблемы и решения текущей архитектуры InsureTech

## Контекст

- `ins-product-aggregator` хранит актуальные тарифы СК в своей базе данных и синхронно опрашивает страховые компании.
- `core-app` обновляет локальную копию тарифов раз в 15 минут, `ins-comp-settlement` — раз в сутки.
- Ночью `ins-comp-settlement` запрашивает у `core-app` все полисы за день для расчётов.
- B2B-партнёры создают нагрузку до 250 RPS.
- Планируется подключить ещё 5 СК (итого 10).

## Проблемы и риски

1. **Каскадные сбои при опросе СК.** Если одна из 10 СК отвечает медленно, это тормозит весь поток запросов. Доступность поиска тарифов падает.
2. **Устаревшие данные.** Копии тарифов обновляются по расписанию: до 15 минут неактуальных цен у `core-app`, до суток — у `ins-comp-settlement`. Это ведёт к ошибкам в расчётах.
3. **Пиковая ночная нагрузка.** При текущей нагрузке от B2B‑партнёров система работает близко к пределу. Ночной пакетный запрос всех полисов за день создаёт резкий всплеск, который может сорвать сроки расчётов и привести к штрафам.
4. **Линейный рост нагрузки на агрегатор.** Каждый входящий запрос порождает множество вызовов к СК. При увеличении числа СК нагрузка растёт пропорционально и становится трудноуправляемой.
5. **Нет гарантий доставки событий.** При сбоях возможны потеря или дублирование данных о полисах, что требует ручного вмешательства.
6. **Сложность масштабирования потребителей.** Добавление новых сервисов требует изменений в существующих компонентах, растёт связанность системы.
7. **Расчёты зависят от `core-app`.** Если `core-app` недоступен ночью, расчёты не выполняются — риск штрафов.

## Решения

| Проблема | Решение |
|----------|---------|
| Каскадные сбои, устаревшие реплики, рост нагрузки | Переход на событийную модель: агрегатор публикует событие об обновлении тарифов, потребители обновляют свои копии по факту появления события |
| Ночной batch, зависимость расчётов | Событие о факте оформления полиса публикуется сразу. `ins-comp-settlement` ведёт реестр непрерывно и независимо от `core-app` |
| Гарантии доставки и дубли | Использование механизма Transactional Outbox: факт изменения и событие фиксируются вместе. Потребители обрабатывают события с защитой от дублей |
| Сложность добавления потребителей | Новые сервисы просто подписываются на нужные события — никаких изменений в поставщиках не требуется |
| Обмен данными с СК по расчётам | `ins-comp-settlement` формирует реестры и акты из накопленных событий и отправляет их в СК по расписанию или пакетно; статусы отправки фиксируются в его базе данных |

### Ключевые архитектурные решения

- **Модель обмена — событийная (EDA) через Kafka.** Используются два основных события: факт оформления полиса и обновление тарифов. Публикация событий происходит через механизм Transactional Outbox, потребление — через стандартные подписки на топики.
- **База данных агрегатора — источник истины по тарифам.** `ins-product-aggregator` обновляет тарифы в своей базе и сразу генерирует событие. Остальные сервисы получают эти данные через Kafka и поддерживают у себя актуальные копии.
- **Публикация событий — часть логики сервисов.** Воркеры, отвечающие за отправку событий, работают внутри самих сервисов и привязаны к изменениям в их базах данных.
- **Копии данных хранятся в базах соответствующих сервисов.** `core-app` хранит копию тарифов для быстрого поиска, `ins-comp-settlement` — для расчётов. Актуализация происходит автоматически по событиям.
- **Единый стек баз данных.** Все сервисы используют PostgreSQL — это упрощает поддержку и эксплуатацию.
- **Синхронными остаются только критически важные операции.** Оформление полиса и работа с персональными данными выполняются синхронно — это необходимо для соблюдения требований по обработке ПДн.
- **Расчёты с СК инициируются из `ins-comp-settlement`.** Сервис собирает данные из событий, формирует пакеты для СК и отправляет их по установленным протоколам. Статусы отправки фиксируются локально.

## Вывод

Текущая синхронная модель с периодической синхронизацией не справляется с ростом числа страховых компаний и текущей нагрузкой. Переход на событийную архитектуру (Kafka + Transactional Outbox) решает проблему каскадных сбоев, устраняет устаревание данных, убирает пиковые ночные нагрузки и делает расчёты независимыми от других сервисов. Единый стек баз данных снижает сложность эксплуатации.
