# Task5. GraphQL API для client-info

## Проблема

Текущий REST API сервиса client-info разбит на множество отдельных ресурсов (документы, родственники и т.д.). Это следствие большого атрибутивного состава карточки клиента (до 500 полей): отдавать всё сразу нельзя — ответ становится слишком тяжёлым, особенно для веб-приложений.

Но из-за такой структуры в одном бизнес-сценарии приходится делать несколько запросов к сервису. Это кратно увеличивает RPS и нагрузку на client-info.

## Решение

Реализуем GraphQL-слой поверх текущих данных. Он сохраняет все возможности REST, но даёт гибкость в выборе полей и позволяет получать связанные данные в одном запросе.

## Покрытие REST-операций

Схема покрывает три основных GET-эндпоинта из Swagger:

- /clients/{id} → query client(id)
- /clients/{id}/documents → query documents(clientId)
- /clients/{id}/relatives → query relatives(clientId)

Это позволяет мигрировать потребителей поэтапно, не меняя логику вызовов.

## Ключевые моменты реализации

- Вложенные поля documents и relatives в типе Client. Теперь можно получить клиента и связанные данные одним запросом.
- Выборочное запрашивание полей. Потребитель берёт только нужные атрибуты — нет передачи лишнего объёма.
- Поля оставлены nullable, чтобы не ужесточать контракт относительно REST. Списки в корневых запросах — не-null (сервис всегда возвращает массив, даже пустой).
- Для дат введён скаляр Date — это фиксирует формат и избавляет от будущих изменений контракта.

## Примеры запросов и ответов

Пример 1. Данные клиента, аналогично GET /v1/clients/{id}.

Запрос:

```graphql
query {
  client(id: "123") {
    name
    age
  }
}
```

Ответ:

```json
{
  "data": {
    "client": {
      "name": "Иван Петров",
      "age": 34
    }
  }
}
```

Пример 2. Клиент вместе с документами и родственниками одним запросом — то, что в REST заняло бы три вызова.

Запрос:

```graphql
query {
  client(id: "123") {
    name
    documents {
      type
      number
      expiryDate
    }
    relatives {
      relationType
      name
    }
  }
}
```

Ответ:

```json
{
  "data": {
    "client": {
      "name": "Иван Петров",
      "documents": [
        {
          "type": "passport",
          "number": "4517 123456",
          "expiryDate": null
        },
        {
          "type": "driverLicense",
          "number": "77 21 123456",
          "expiryDate": "2030-05-12"
        }
      ],
      "relatives": [
        {
          "relationType": "spouse",
          "name": "Мария Петрова"
        },
        {
          "relationType": "child",
          "name": "Анна Петрова"
        }
      ]
    }
  }
}
```

Пример 3. Только документы клиента, аналогично GET /v1/clients/{id}/documents — без загрузки самого клиента.

Запрос:

```graphql
query {
  documents(clientId: "123") {
    number
    issueDate
  }
}
```

Ответ:

```json
{
  "data": {
    "documents": [
      {
        "number": "4517 123456",
        "issueDate": "2014-06-20"
      }
    ]
  }
}
```

Пример 4. Родственники через корневой запрос, аналогично GET /v1/clients/{id}/relatives.

Запрос:

```graphql
query {
  relatives(clientId: "123") {
    relationType
    age
  }
}
```

Ответ:

```json
{
  "data": {
    "relatives": [
      {
        "relationType": "spouse",
        "age": 33
      },
      {
        "relationType": "child",
        "age": 7
      }
    ]
  }
}
```

В примере 2 видно главное преимущество: один HTTP-запрос возвращает данные, ради которых в REST пришлось бы вызвать три эндпоинта. А если в каком-то сценарии нужен только номер паспорта — потребитель запрашивает одно поле из одного типа, не тянет весь объект.

## Риски и что учесть

Вложенные поля резолвятся отдельно. При наивной реализации это может дать лишние запросы к БД. На текущем объёме данных это не критично, но при масштабировании стоит внедрить batching (например, DataLoader), чтобы избежать проблемы N+1.
