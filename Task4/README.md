# Проектирование продажи ОСАГО

## 1. Контекст и проблема

Бизнес запускает оформление ОСАГО онлайн. Пользователь заполняет заявку, сервис опрашивает все доступные страховые компании (СК), офферы отображаются у пользователя сразу по приходу от каждой СК. Максимум ожидания — 60 секунд. Пик — 2 500 одновременных пользователей. API каждой СК: два REST-эндпоинта — создать заявку и получить оффер.

По решению команды выделяется отдельный сервис osago-aggregator для взаимодействия со СК; остальная функциональность оформления остаётся в core-app. Подход к интеграциям — как в Task 3: событийная модель через Kafka и Outbox.

Ключевые сложности:

- СК отвечают в разное время (от секунды до минуты) — офферы нужно доставлять пользователю потоком, по одному по приходу.
- При пике до 25 000 одновременных запросов к СК (2 500 пользователей × 10 СК) — состояние заявок нужно хранить и не терять при сбоях.
- СК могут быть недоступны или отвечать медленно — нужна защита от каскадных сбоев и контроль общего времени ожидания.
- Один клиент (партнёр или скрипт) может перегрузить сервис своими запросами — нужна защита на входе.

## 2. Архитектура решения

### Компоненты

Компонент | Технология | Назначение
----------|------------|-----------
osago-aggregator | Java Spring Boot | Отправка заявок в СК, опрос офферов, публикация результатов в Kafka
osago-aggregator-db | PostgreSQL | Заявки, статусы по каждой СК, офферы, outbox

Хранилище нужно: объём одновременных заявок и долгоживущий опрос СК не позволяют держать состояние в памяти — оно потерялось бы при рестарте сервиса.

### Интеграции и события

core-app и osago-aggregator связаны двумя способами, под разные задачи:

- REST — core-app создаёт заявку в агрегаторе и сразу получает её идентификатор, чтобы открыть поток офферов для пользователя.
- Kafka, топик osago-offers — агрегатор публикует офферы по мере ответов СК и финальное событие, когда ответили все. Core-app слушает топик и стримит офферы пользователю.

Финальное событие нужно, чтобы закрыть поток раньше дедлайна, если все СК успели ответить: сколько всего СК должно ответить, знает только агрегатор. Если же дедлайн наступил раньше — core-app закрывает поток по собственному таймеру в 60 секунд, ничего не дожидаясь.

Публикация событий — через Outbox: событие не теряется при сбое.

### API для веб-приложения

Эндпоинт | Протокол | Назначение
---------|----------|-----------
POST /api/v1/osago/applications | REST | Отправка формы
GET /api/v1/osago/applications/{id}/offers | SSE | Поток офферов — по одному, сразу по приходу

SSE выбран вместо WebSocket: поток однонаправленный (сервер → клиент), проще в реализации.

### Отказоустойчивость и контроль нагрузки

Направление | Паттерны | Почему
-----------|----------|-------
osago-aggregator → СК | Timeout, Circuit Breaker, Retry, Rate Limit | Упавшую СК перестаём опрашивать; сбои повторяем; не превышаем квоты СК
core-app → osago-aggregator | Timeout, Circuit Breaker, Retry | Создание заявки — короткая операция; при сбое быстро возвращаем ошибку
Вход в core-app | Rate Limit по client_id / IP | Один клиент не может перегрузить сервис и отнять ресурсы у остальных

Rate Limit на вход core-app нужен: без него один партнёр или скрипт может «съесть» всю пропускную способность, и остальные пользователи не смогут оформить ОСАГО.

Rate Limit на выход к СК — это управление собственной очередью и соблюдение контрактов с партнёрами. Полагаться на 429 от СК нельзя: потерянный по лимиту ответ — потерянный оффер в рамках 60-секундного дедлайна. Дополнительно к Rate Limit используется пул соединений к каждой СК — он ограничивает число одновременных запросов (параллелизм), а Rate Limit ограничивает частоту (RPS). Пул нужен всегда, Rate Limit — когда СК предъявляет требования по частоте.

При пике часть заявок встаёт в очередь к СК. Если очередь не успела обработаться за 60 секунд — заявка отменяется по таймауту, пользователь получает офферы от тех СК, которые успели ответить.

### Дедлайн 60 секунд

Дедлайн обеспечивается контролем времени на нашей стороне, а не скоростью СК:

- Заявки во все СК отправляются параллельно сразу после создания.
- Все вызовы к СК ограничены таймаутами; Retry и Circuit Breaker работают внутри общего бюджета времени.
- core-app держит таймер 60 секунд и закрывает поток по его истечении — независимо от ответов СК. Если все СК ответили раньше, агрегатор сообщает об этом финальным событием, и поток закрывается раньше.
- Офферы, пришедшие после закрытия потока, сохраняются для взаиморасчётов, но пользователю не показываются.

Считаем, что сервисы работают в одном экземпляре — распределение работы между инстансами выходит за рамки задания.

## 3. Поток оформления ОСАГО

1. Пользователь отправляет форму → REST в core-app.
2. core-app сохраняет заявку, создаёт её в osago-aggregator и открывает SSE-поток.
3. Агрегатор параллельно рассылает заявки во все СК и опрашивает их до оффера или 60 секунд.
4. Каждый оффер публикуется в Kafka → core-app отправляет его клиенту по SSE.
5. Все СК ответили или истекли 60 секунд — поток закрывается, пользователь выбирает оффер.
